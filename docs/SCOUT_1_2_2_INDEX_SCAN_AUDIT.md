# Scout 1.2.2 — indexing, scanning and reporting audit

**Audit scope:** user-supplied Scout 1.2.1 source archive (first attachment), using the second user-supplied `wayback-machine-downloader` as a *reference*, not a drop-in replacement. This report describes the verified source behavior, the changes included in the v1.2.2 overlay, and tests actually executed. No live Internet Archive indexing or multi-day test was performed.

## Executive conclusion

The scan/report failure was partly a scheduling and state-coverage defect, not merely a presentation bug: primary downloads deferred scanning until the network pool drained; subsequent scan runs did not automatically include prior saved documents; document-less saved captures could fall between work queues; and a SQLite scan-match failure could mark a capture as scanned without durable match records. Independently, transient CDX responses could cause wasteful endpoint/format churn, especially HTML service-error pages, and certain permanent/invalid responses could falsely imply no inventory.

The principal correction is **durable scan evidence**: each saved eligible body should have a persisted, per-scan-run score row (including score zero), or a visible retryable error. Local scanning must be able to progress when Wayback is unavailable. Indexing is complete only when its coverage checkpoints say so, not when the latest request returns no rows or a failure is misclassified.

## Confirmed findings and corrective actions

| Impact | Evidence in the supplied code | v1.2.2 action |
|---|---|---|
| **Critical: network-dependent scanner** | `downloads/downloader.py` originally submitted acquisition with `scan_now=False` and drained the pending queue after the download pool exited. During extended Wayback failures this meant accumulated bodies remained unscanned. | Download workers now parse/score before persisting; previously saved pending work drains independently. `operations.py` scans existing bodies *ahead of indexing* when continuing an existing project. |
| **Critical: empty scan runs and reports** | New `scan_runs` could be created without scoring already persisted `documents`. A zero-hit latest run overwrote the root `matches_ranked.txt`, obscuring prior discoveries. | `operations.py` backfills saved docs lacking a per-run score row; report summary distinguishes no scans from genuine zero hits. Per-run outputs remain; `last_nonempty_matches_ranked.txt` separately preserves prior discoveries. |
| **Critical: missing-document gap** | Pending scan discovery centered on `downloaded_unscanned` while rescanning enumerated `documents`, missing `downloaded` captures whose document insert previously failed. | Pending scanner also includes `downloaded AND documents.id IS NULL`; missing local file is explicitly marked retryable reacquisition. |
| **Critical: non-atomic scan checkpoint** | A failure between document persistence and match persistence could leave a capture marked `downloaded` without scored evidence. | Per-capture SQLite savepoint rolls back document/match/state updates together; error records persist after rollback. Scan completion checks for unscored saved bodies and unresolved scan errors. |
| **Critical: false index completeness** | Generic CDX 403 or an error dictionary could be read as empty inventory. Temporary failed paged-count probes could abandon otherwise valid paging plans. | Refuse generic 403 as complete; retain failed checkpoint, surface site issue. Reject CDX error objects as empty rows. Retry page count without inventing unavailable pagination. Report unfinished `index_coverage`/legacy `index_state` rows explicitly. |
| **High: ineffective CDX recovery** | Headerless HTTP 503 followed host-wide coordinated pauses; HTML errors could provoke duplicate JSON/text requests at the same endpoint. | Headerless 503 uses bounded HTTP-status retries; explicit Retry-After/429 use coordinated pauses. Detect HTML service-error responses and skip alternate format at that endpoint; stop same-host endpoint churn on rate-limit deferral. |
| **High: lost rescan progress** | Re-running an interrupted rescan could create a new `scan_run`, repeating completed scoring. | Reuse compatible interrupted runs and skip documents with committed score rows, even if the score was zero. Scope includes targets and per-target CDX query signatures. |
| **High: needless memory and work** | Rescan loaded 1,000 complete `documents` records per page, and large numbers of futures could retain multiple large bodies. | Page 16 document rows; limit in-flight parsing/scoring to an estimated 64 MiB local working set, allowing a single oversized file rather than dropping evidence. Reuse scans backed by durable match rows. |
| **High: per-target signature mismatch** | Download/retry selection used the global `cdx_query_signature(config)`, which could exclude captures indexed with a site-specific override. | Temp SQLite target/signature scope tables select every eligible configured site without large in-memory ID lists. Cumulative progress and retry sweeps use the same scope. |
| **Medium: opaque status** | Raw indexed capture totals alone do not imply that CDX enumeration was finished. | Report displays completed/unfinished inventory checkpoint windows and a separate scanned-outcomes diagnostic. |

### Content classification preserved

The order remains CDX inventory -> indexed-resource text/media classification -> text replay validation -> HTML/text parsing/keyword scoring -> optional subsequent media acquisition. Indexed confidently classified binary/media resources are still deferred or skipped rather than written as bogus `.txt`; actual replay bytes are still checked for nontext content. No text collapse or extra-media collapse policy has been relaxed, and v1.2.2 does not change the database schema version (9).

### Connectivity and completeness policy

- `503` without Retry-After is treated as a finite generic HTTP error at the request layer, not indefinite coordinated global rate-limit pauses. An actual `429` or `503` carrying Retry-After still receives host-coordinated recovery; these waits respect configuration and cannot be eliminated safely by client code.
- Transient indexing failures keep their saved page/range/cursor instead of treating errors as an empty result; persistent recovery can continue indefinitely if explicitly enabled. This ensures progress survives network outages, **but cannot force a broken or throttled remote service to produce data**. User Stop remains functional.
- Generic `403` is visible and the window stays **incomplete** rather than misrepresented as permanently empty. This is intentionally a surfaced blocker: bypassing Wayback access policy or guessing absent captures would violate evidence integrity.
- Downloaded and scanned bodies are locally recoverable before another index pass in an existing project. A fresh project with no saved data necessarily depends on a working CDX response.
- Scanning is text-only until the separate media phase, and score-zero rows are required for complete evidence. File and DB failures remain resumable; missing bodies are not reported as scanned.

## Reference downloader comparison

The attached Ra downloader has a nominal request admission pace of `StrictLimiter(480/60)` (8 starts per second), a concurrent request limiter of 10, Timemap pagination, and bounded request retry logic. Its design supports the conclusion that **bounded concurrency and avoiding duplicate CDX requests** matter more than increasing worker counts indefinitely. Scout already has nominal 0.125-second replay pacing under its defaults; this is a starts-per-second budget, *not* a promise of 8 verified saves per second. Replacing Scout's inventory, text/media classifier, SQLite transaction semantics and project resume checkpoints wholesale with the reference implementation would be unsafe and is not attempted.

## Executed verification

1. Full local regression suite: **306 passed, 6 skipped, 12 passed subtests** using `pytest` on Linux/Python 3.13.5; canonical `scripts/run_tests.py` **312 run, 0 failures, 0 errors, 6 skipped**. `python -m compileall -q archive_scout` and `python scripts/verify_release.py` passed.
2. Targeted fault-injection tests: database failure while persisting scan matches rolls back all scan state; missing local file is returned for download; formerly stranded `downloaded` captures without document records are recovered; interrupted rescan restarts without reprocessing scored documents; CDX generic 403 remains incomplete; incomplete coverage appears in reports; saved body is scanned before a simulated CDX indexing outage; per-target CDX signature variations remain selected for download/retry.
3. **Local loopback, 120 archived text captures**: patched Scout 1.2.2 completed 120 verified saves, 120 documents and 120 durable score rows in **14.964s (8.019/s)**; acquisition 14.962s; final scan drain 0.003s; SHA-256 verified. Early / middle / late validated acquisition phases: **8.083 / 7.990 / 7.989 saves/s**. Control using the supplied v1.2.1 source: 120 validated saves in **15.125s (7.934/s)** with a **0.172s** post-download scanning tail. This short smoke test measures correct coupling and tail reduction, **not long-run speed gains**.
4. Offline synthetic benchmark (no HTTP): 15,000 CDX fixtures parsed and upserted in **0.580s**, peak tracked Python allocations **4.46 MiB** for that operation; 15,000-row parse only **0.344s**; repeated parse/no-op upsert **0.470s** with zero changed rows; 1,500 synthetic report result rows, JSON export **0.101s**. These small figures cannot establish real-world performance under large archived bodies, complex rules, or millions of rows.

## Not verified and remaining risks

- No multi-day Wayback operation, 650,000-capture resume, multi-million capture database, throttle storm, or production proxy disruption could be reproduced. Sustained 8/s remains a goal, not a measured live-service result.
- No native Windows/macOS GUI or GitHub Actions CI run was performed in this environment; run the repository's existing matrix after uploading the patch. Skipped tests require checking their prerequisites.
- The CDX service may continue returning 429/503, fail on individual pages, or explicitly forbid queries. Automatic recovery cannot fix remote data unavailability. A persistent retry policy may intentionally keep displaying retries rather than finishing; this now preserves unfinished coverage and avoids common duplicate work, but is not proof of successful indexing.
- Worker memory budgeting is an estimate and excludes shared interpreter/SQLite caches; a single extremely large document can exceed the budget by design. True RSS should be monitored on realistic long workloads.
- A fresh keyword set requires reading each retained body at least once to preserve match semantics; no zero-work shortcut can guarantee correct raw-source/visible-text matches. Existing score-zero coverage avoids repeated rescans on Resume.
- Target-specific worker and replay-delay overrides are indexed and preserved, but acquisition workers continue using invocation-level settings; this patch fixes selection/completeness without redesigning concurrent per-target pacing.
- `retain_scan_details=False` does not itself suppress every detail: `ReportConfig.store_keyword_counts`, `.store_snippets` and related flags deliberately retain fields if corresponding report outputs are still enabled. The patched scanner continues to persist these details by default. A future lean-storage optimization must honor enabled report fields and historical rescans without deleting existing evidence; this release does **not** claim that optimization.
- A few endpoint/format fallbacks remain for non-HTML malformed CDX bodies because isolated serialization errors can legitimately be recoverable; the fix only avoids proven duplicate failure patterns. A remote service in a sustained outage can still dominate wall-clock time.
- Changing text rules/target scope creates a different scan identity, as expected. Avoid editing active project settings mid-run without backing up project data.

## Upgrade guidance

**Back up and stop the application** before replacing source files. Apply the patch files relative to the root of the original Scout 1.2.1 source; keep the project folder (especially `archive_scout.sqlite3`, WAL/SHM, and `captures/`) intact. It is safer to use the project's built-in consistent backup than copying an open SQLite database. The v1.2.2 change does not require a database migration; the existing import path, command line, GUI, text/media routing and saved settings remain the same. Launch the same project folder and use Resume/Rescan; a completed job's matching coverage is reused and missing coverage is recovered. Inspect `reports/summary.txt`, the per-run scan report directory, and `last_nonempty_matches_ranked.txt` separately.

### Recommended future field verification

For a representative existing project, capture **network request starts, HTTP status mixes, retry categories, completed/unfinished CDX coverage windows, newly validated saves, persisted scans and scores, bounded queue size, RSS, disk growth and SQLite commit/WAL time** at 0%, 10%, 50%, 90% and completion. Compare aggregate and rolling 30-second rates, distinguishing wire attempts from successfully scored saves; simulate 503 with/without Retry-After, connection resets, interrupted database transactions, and restart. A localhost test cannot substitute for these live-service measurements.
